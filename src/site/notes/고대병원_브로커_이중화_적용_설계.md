# 고대병원 CISInBroker / CISOutBroker 이중화 적용 설계

기준 소스
- 대상: `D:\KUMC\ANAM\CIS_SI\고대병원\CISInBroker`, `…\CISOutBroker`
- 참조: `D:\CMC\서울성모\CIS_ETC\CISDualBroker\trunk\Source\CISDualBrokerLib`
- DB: `D:\doc\CIS_1400\doc\Database`

전제 (확정된 방향)
- **EHR REST API Gateway 연동 방식은 그대로 유지**한다. 이중화 프레임워크만 도입하고, EMR 접점은 Patcher 콜백으로 감싼다.
- 두 노드는 **동일한 CIS Oracle DB** 를 바라본다. DB 자체 이중화(RAC/DataGuard)는 본 설계 범위 밖.
- 본 문서는 설계/변경 항목 정의까지이며 실제 소스 수정은 포함하지 않는다.

## 0. 기본 전략 — 왜 "재작성"이 아니라 "재배치"인가

고대병원 CISOutBroker는 이미 CISDualBroker 계열에서 파생된 코드입니다. 근거:

| 근거 | 위치 |
| --- | --- |
| `CISBrokerData_Order/Exam/Instance`, `CISOutbroker_JOB` 클래스가 필드 단위까지 동일 | `CISOutBrokerHelper.h` vs `CISDualBrokerLib\CISBrokerData.h` |
| `PkgOrder.GetOrderByOCISKey` → `PkgExam.GetExamByOCISKey` → `PkgInstance.GetInstanceList` 호출 순서 동일 | `CISOutBrokerHelper.cpp` 228/296/344행 |
| `GetOutboundDetailData`에서 `I_ORD0001` 로 OrderKey 추출하는 로직이 문자 단위로 동일 | `CISOutBrokerHelper.cpp` 473행~ |
| `PKGBROKER.GetCommander` 문자열이 에러 로그에 그대로 잔존 | `CISOutBrokerHelper.cpp` 537행 |

즉 **CISDualBroker에서 이중화 계층을 걷어낸 것이 고대 버전**입니다. 따라서 작업의 본질은 새 기능 개발이 아니라, 걷어낸 계층을 되돌리고 고대 고유 로직(REST 연동, 판독문 처리)을 Patcher 위치로 옮기는 **재배치**입니다.

```
[현행 고대]                          [목표]
CISOutBrokerU.exe                    CISOutBrokerU.exe
 └ Worker (1 thread)                  ├ CISBrokerModuleU.dll (이중화 계층, 무수정 재사용)
    ├ Helper.GetJob   ─┐              │  ├ AliveChecker   : Heartbeat / Death / Active 승격
    ├ SetExamResult    │ 전부          │  ├ JobCommander   : Active만 배분 + failover 이관
    └ UpdateJobResult ─┘ 한 덩어리      │  └ JobWorker      : 자기 BC_KEY 작업만 처리
                                       └ CISBrokerJobPatcherForKUMC (신규, 고대 고유 로직만)
                                          └ OnOutbrokerRutine() ← 기존 SetExamResult() 이식
```

# A. DB 계층

## A-1. 이중화 테이블 3종 생성

**대상**: 고대병원 CIS DB (`cis2011` 스키마)
**원본**: `CISDualBroker\doc\브로커 이중화 DB Script\Outbroker 이중화 테이블.sql`

생성 대상:

| 오브젝트 | 용도 |
| --- | --- |
| `T_BROKERCOMMANDER` + `SQ_T_BROKERCOMMANDER` + 인덱스 2개 | 브로커 노드 상태/Heartbeat |
| `T_BROKERWORKERJOB` + `SQ_T_BROKERWORKERJOB` + 인덱스 1개 | Outbroker 작업 큐 |
| `T_INBROKERWORKERJOB` + `SQ_T_INBROKERWORKERJOB` + 인덱스 1개 | Inbroker 작업 큐 |

**주의사항**

- 원본 스크립트에는 `tablespace` 지정이 없습니다. 고대 CIS DB의 기존 테이블은 `&DATA_TABLESPACE` / `&INDEX_TABLESPACE` 로 분리되어 있으므로(`SetupScript\Server\Schema\SchemaBuild.sql` 참조), 동일 규칙에 맞춰 tablespace 절을 추가해야 합니다.
- `BC_ENDDT` / `BWJ_ENDDT` 의 기본값 `TO_DATE('99991231235959','yyyymmddhh24miss')` 는 CIS 공통 논리삭제 규칙입니다. 모든 조회 조건이 여기에 의존하므로 임의 변경 금지.
- `T_BROKERWORKERJOB`, `T_INBROKERWORKERJOB` 은 처리 완료 후에도 행이 남습니다. 일 처리량 × 보존기간 산정 후 **아카이빙/삭제 배치**를 별도 준비해야 합니다 (원본에도 없는 부분).

## A-2. `PKGBROKER` 패키지 배포

**원본**: `package.pkgbroker.sql` (스펙) → `packagebody.pkgbroker.sql` (바디) 순서로 컴파일

프로시저 15개 (`SetCommander`, `RmvCommander`, `UpdCommander`, `UpdCommanderAlive`, `GetCommander`, `Inbroker_AddJob/GetJob/GetJobCount/UpdJobResult/ChangeJobWorker`, `Outbroker_AddJob/GetJob/GetJobCount/UpdJobResult/ChangeJobWorker`)

**주의사항**

- `PKGBROKER`는 **CIS 1400/2000 표준 패키지가 아닙니다.** `SetupScript\Server\Package` 및 Patch 폴더(2013~2023) 전체에 존재하지 않습니다. 따라서 **CIS 정기 패치를 적용할 때마다 PKGBROKER가 유실되지 않는지 확인**해야 하고, 사이트 인수인계 문서에 별도 명기가 필요합니다.
- `GetCommander`는 동적 SQL(`vvSQL` 문자열 결합)에 `pvCommandType`, `pvCommander`를 그대로 붙입니다. 값이 애플리케이션 내부 상수와 GUID이므로 실사용상 문제는 없으나, 보안 점검 대응이 필요하면 바인드 변수 방식으로 개선하는 것을 권장합니다.
- `SetCommander`는 `SQ_T_BROKERCOMMANDER.nextval`을 사용하므로 시퀀스 누락 시 등록 자체가 실패합니다. 배포 검증 항목에 포함하십시오.

## A-3. `PkgInterface.GetOutBoundList` 시그니처 확인

**현행 고대 호출부**: `CISOutBrokerHelper.cpp` 421행

```
PkgInterface.GetOutboundList(pvHandleFlag, pvStartDateTime, pvEndDateTime)   ← ActionCode 필터 없음
```

**CISDualBrokerLib 호출부**: `CISBrokerJobCommander.cpp` 1502~1508행

```
PkgInterface.GetOutboundList(pvHandleFlag='0', pvStartDateTime, pvEndDateTime, pvActpValue=ActionCode목록)
```

`pvActpValue`는 `SetupScript\Server\Package\package_pkginterface.sql` 236행에 `IN VARCHAR2 := NULL` 기본값으로 이미 선언되어 있고, 바디(1062행~)도 `pvActpValue IS NULL` 분기를 갖고 있습니다.

**확인 필요**: 고대 운영 DB에 배포된 `PkgInterface` 버전이 `pvActpValue`를 지원하는지 실측 확인. 미지원이면 `SetupScript` 또는 `Patch\2023.10.11\package_body_pkginterface.sql` 기준으로 선행 패치.

## A-4. Outbound 재처리(HandleFlag) 정책 재정의

현행 고대는 Worker가 EHR 전송에 성공/실패한 시점에 `SetUpdOutboundFlag`로 `'5'`(성공) / `'4'`(실패)를 기록합니다.

CISDualBrokerLib는 **Commander가 작업 큐에 넣는 데 성공한 시점**에 원본 Outbound를 `'5'`로 마킹하고, 실제 처리 결과는 `T_BROKERWORKERJOB.BWJ_RESULT`에만 남깁니다.

→ **의미가 달라집니다.** `HandleFlag=4`만 보고 재처리하던 운영 스크립트(`Database\HelpScript\아웃바운드 재처리 스크립트.txt`)가 무력화됩니다.

**결정 필요 항목**

| 안 | 내용 | 장단 |
| --- | --- | --- |
| ① 원본 유지 | Patcher가 처리 완료 시 `SetUpdOutboundFlag`를 추가 호출해 기존 의미 유지 | 기존 운영 스크립트 그대로. 단 Outbound 1건에 대해 flag가 5→5로 중복 갱신 |
| ② 큐 기준 전환 | `BWJ_RESULT IS NOT NULL AND BWJ_ENDDT < 9999…` 기준으로 재처리 스크립트를 새로 작성 | 구조상 깔끔. 운영 문서/스크립트 개정 필요 |

권장은 ②이며, 전환 기간에는 ①을 병행해 이중 기록하는 것이 안전합니다.

# C. 설정 체계

## C-1. `ModuleConfig.ini` 신규 도입 — 브로커 신원 관리

이중화의 **가장 중요한 신규 개념**입니다. 각 노드는 자기 GUID를 파일에 보관해야 재시작 후에도 동일 브로커로 인식됩니다.

**파일 위치** (`CISBrokerFactory::RegisterBroker` 121~131행에 하드코딩):

```
<모듈경로>\Config\InBroker\ModuleConfig.ini
<모듈경로>\Config\OutBroker\ModuleConfig.ini
```

**형식** (서울성모 실제 파일):

```ini
[InBroker]
Name=8C121EB7-761C-48D8-8ABE-D0B5AC71AAD8
Path=C:\INFINITT\CISDual-InBroker\
IP=172.17.33.54
```

**동작** (`RegisterBroker` 136~166행)

1. `Name` 이 비었거나 `Path`가 현재 모듈 경로와 다르면 → `GenerateGUID()` → `PKGBROKER.SetCommander(state='Standby')` → INI에 Name/Path/IP 기록
2. 이후 `PKGBROKER.GetCommander(strUID)` 로 `BC_KEY`, `BC_STATE`, `BC_ALIVEDT` 를 `g_BrokerInfo`에 적재

**⚠ 반드시 인지할 함정** — `RegisterBroker` 136~140행에 조건문 버그가 있습니다.

```cpp
if(strUID.IsEmpty() ||
   strPath.CompareNoCase(CISGF::GetModulePath(NULL)) != 0 ||
   strIP   != CISGF::GetHostIP())
if(strPath != CISGF::GetModulePath(NULL))     // ← 세미콜론 없이 if 두 개가 연속
{
    strUID = GenerateGUID();
    ...
}
```

첫 `if` 에 본문이 없어 **두 번째 `if` 만 실질적으로 동작**합니다. 결과적으로 "IP가 바뀌어도 경로가 같으면 재등록하지 않는" 동작이 됩니다. 서버 IP 변경 시 `T_BROKERCOMMANDER.BC_LASTWRITERIP` 만 갱신되고 신원은 유지되므로 현재 운영상 문제는 없지만, 의도된 동작인지 확인 후 고대 적용 시 정리할지 결정해야 합니다.

**배포 시 주의**: 1호기 설치 폴더를 그대로 복사해 2호기를 만들면 **`Name`(GUID)이 동일**해져 두 노드가 같은 브로커로 인식됩니다. 반드시 2호기의 `ModuleConfig.ini`에서 `Name` 값을 지우고 기동하십시오. 설치 가이드에 필수 명기 대상입니다.

## C-2. 기존 `Config.xml` → `BROKER_SETTING` 매핑 계층 추가

고대는 XML(`SKXml`, `ConfigManager`), CISDualBroker는 INI(`CISIni`) 를 씁니다. **XML 방식을 유지**하고 변환 함수만 추가하는 것을 권장합니다 (운영 배포 파일 형식 변경 최소화).

| `BROKER_SETTING` 필드 | 고대 `ConfigManager::CONFIG` 대응 | 비고 |
| --- | --- | --- |
| `m_eBrokerType` | (없음) | 코드 상수로 지정: `broker_type_Inbroker` / `broker_type_Outbroker` |
| `m_CISDBINFO.m_eDBType` | (없음) | `broker_dbtype_Oracle` 고정 |
| `m_CISDBINFO.m_strDBName/UserID/UserPW` | `m_CIS.strDB_Name / strDB_ID / strDB_PW` | 1:1 |
| `m_EMRDBINFO` | **(대응 없음)** | 고대는 EMR을 DB가 아닌 REST로 접근. **빈 값으로 두고 Patcher가 무시** |
| `m_nSearchPeriod` | `m_CIS.nSearchDays` | 1:1 (OutBroker만 존재. InBroker의 `ConfigManager.h`에는 없으므로 신규 추가 필요) |
| `m_dwEtcOption` | (없음) | InBroker 취소 루틴 옵션. 고대 적용 여부 판단 후 결정 |

**신규 XML 노드 제안**

```xml
<Broker>
  <AliveCheckSec>20</AliveCheckSec>   <!-- 선택: D-6 참조 -->
</Broker>
```

**⚠ `m_EMRDBINFO` 관련 필수 확인**: `CISBrokerFactory::CreatebrokerObject` 는 `pPatcher->InitInstance()` 를 호출합니다. CMC Patcher는 여기서 EMR DB에 접속하지만, 고대 Patcher는 **REST이므로 DB 접속 없이 TRUE 반환**하도록 구현해야 합니다. 반환값이 FALSE면 Factory 전체가 기동 실패합니다.

## C-3. 자격증명 하드코딩 제거

`CISOutBroker\ConfigManager.cpp` 22~28행의 `Default()`에 DB 비밀번호(`infinitt`)와 EHR API Key가 평문 상수로 박혀 있습니다.

이중화로 **동일 설정이 2개 노드에 복제**되므로 노출면이 2배가 됩니다. 이번 작업과 함께 `Database\HelpScript\암호화` 방식 적용을 검토하십시오. (필수는 아니나 보안 점검 시 지적 대상)

# D. CISOutBroker 애플리케이션 개조

## D-1. `CISBrokerJobPatcherForKUMC` 신규 클래스

**핵심 항목입니다.** 기존 `Worker::SetExamResult()` 를 통째로 Patcher로 옮깁니다.

```cpp
class CISBrokerJobPatcherForKUMC : public CISOutBrokerJobPatcher
{
public:
    virtual BOOL InitInstance();                                        // REST이므로 TRUE만 반환
    virtual BOOL OnOutbrokerRutine(CISOutbroker_JOB* pJob, CString& strResultComment);
    void SetConfig(const ConfigManager::CONFIG& cfg);
protected:
    CString GetWorkCode(LPCTSTR lpszCisActionCode, CISOutbroker_JOB* pJob);   // Worker.cpp 90행 이식
    CString GetEquipCode(CISOutbroker_JOB* pJob);                            // Worker.cpp 139행 이식
    CString GetReportText(CISOutbroker_JOB* pJob);                           // Worker.cpp 195행 이식
    ConfigManager::CONFIG m_Config;
};
```

**시그니처 대응이 이미 맞습니다.**

| 현행 고대 | 목표 |
| --- | --- |
| `BOOL Worker::SetExamResult(CISOutbroker_JOB* pJob)` | `BOOL OnOutbrokerRutine(CISOutbroker_JOB* pJob, CString& strResultComment)` |

`CISOutbroker_JOB` 타입이 양쪽 동일하므로 **함수 본문(`Worker.cpp` 147~193행)은 거의 그대로 이식**됩니다. 추가할 것은 실패 시 `strResultComment`에 사유를 채우는 코드뿐입니다. 이 값이 `T_BROKERWORKERJOB.BWJ_RESULT`(VARCHAR2 255)에 기록되므로 **255바이트 초과 시 잘라야** 합니다.

## D-2. `CISOutbroker_JOB` 필드 차이 해소 ★ 최대 난이도

두 타입은 이름이 같지만 필드가 다릅니다.

| 필드 | 고대 `CISOutBrokerHelper.h` | DualBrokerLib `CISBrokerData.h` |
| --- | --- | --- |
| 작업 키 | `m_nOutboundKey` | `m_nJobKey`, `m_nInferfaceKey` |
| 처방 | `m_Order` | `m_Order` (동일) |
| 검사 | `m_Exams` | `m_Exams` (동일) |
| **판독문** | **`m_Reports` (CArray\<CISBrokerData_Report\*\>)** | **없음** |

고대 `SetExamResult()`는 `GetReportText(pJob)` 로 판독문 본문을 만들어 EHR에 전송합니다. 즉 **판독문 없이는 기능이 성립하지 않습니다.** 그러나 DualBrokerLib의 `CISOutBrokerJobWorker`는 `PkgReport.GetReportHistoryByOrder` 를 호출하지 않습니다 (Order / Exam / Instance / Volume 만 수집).

**선택지**

| 안 | 내용 | 평가 |
| --- | --- | --- |
| **① Patcher 내부 조회 (권장)** | `OnOutbrokerRutine` 안에서 별도 `CISDatabase` 로 `PkgReport.GetReportHistoryByOrder` 를 직접 호출 | **CISBrokerModuleLib 무수정.** 서울성모와 라이브러리 공유 유지. DB 커넥션 1개 추가 |
| ② 라이브러리 확장 | `CISBrokerData.h`에 `m_Reports` 추가 + Worker에 조회 로직 추가 | 서울성모 재빌드/재배포 필요. 라이브러리 분기 발생 |

**①을 강력히 권장합니다.** OrderKey는 `pJob->m_Order` 에 이미 들어 있으므로 조회가 가능하고, 기존 `CISOutBrokerHelper::GetReport()` (595행) 를 그대로 옮겨 쓸 수 있습니다.

`m_nOutboundKey` → `m_nInferfaceKey` 는 단순 필드명 치환입니다 (둘 다 `t_OutboundDataGroup.ODG_Key`).

## D-5. 재시도(Retry) 정책 재설계

현행 `RetryManager`는 **메모리 큐**(`CList<LPRETRY_INFO>`)입니다. 노드가 죽으면 재시도 대기 건이 함께 소멸합니다.

이중화 도입 후에는 실패 시 `BWJ_RESULT`에 사유만 남고 `BWJ_ENDDT`가 채워져 작업이 종료됩니다. **자동 재시도가 사라집니다.**

**결정 필요 항목** — 다음 중 선택:

| 안 | 내용 |
| --- | --- |
| ① 재시도 포기 | 실패 건은 운영자가 `BWJ_RESULT` 조회 후 수동 재처리 |
| ② Patcher 내 재시도 | `OnOutbrokerRutine` 안에서 N회 재시도 후 최종 결과 반환. 단순하지만 Worker 스레드를 점유 |
| ③ 미완료 유지 | 실패 시 `UpdJobResult`를 호출하지 않아 `BWJ_ENDDT`를 9999로 남김 → 다음 폴링에서 재조회됨 |

③은 코드 변경 없이 가능하지만 **영구 실패 건이 큐를 막습니다**(`Outbroker_GetJob` 이 `BWJ_KEY` 오름차순 10건씩 조회). 실무적으로는 ②(3회 정도) + ①(운영 절차) 조합을 권장합니다.

## D-6. Alive 주기 상수의 하드코딩

`CISBrokerAliveChecker.cpp` 4~10행:

```cpp
#ifdef _DEBUG
    #define TIME_ALIVE_CHECK   10
    #define TIME_ALIVE_MARKING  2
#else
    #define TIME_ALIVE_CHECK   20
    #define TIME_ALIVE_MARKING  2
```

컴파일 타임 상수입니다. 고대 운영 환경(네트워크 지연, DB 부하)에서 20초가 부적절하면 **재빌드가 필요**합니다.

**튜닝 시 제약**: `TIME_ALIVE_MARKING`(2초) < `TIME_ALIVE_CHECK`(20초) 관계가 유지되어야 하며, 최소 3~5배 여유를 두어야 오탐(정상 노드를 Death로 판정)을 막습니다.

# E. CISInBroker 애플리케이션 개조

## E-1. 역할 분리 — Worker 로직의 3분할

현행 고대 InBroker `Worker` 는 다음을 **한 스레드에서 순차 처리**합니다.

```
UserRutine()   : REST GET /user/new → PkgUser.CheckUserInfo → PkgUser.SetUserInfo_SMC → REST POST /user/prss
OrderRutine()  : REST GET /ordr/new → IsExistDepartment/IsExistExamCode/IsExistPatient/IsExistUser
                 → PkgMaster.SetExamDept / SetExamCode / PkgPatient.SetPatientInfo_SMC / PkgUser.SetUserInfo_SMC
                 → PkgOrder.SetOrder → REST POST /ordr/prss
```

CISDualBrokerLib 구조에서는 이것이 셋으로 나뉩니다.

| 현행 위치 | 목표 위치 | 실행 노드 |
| --- | --- | --- |
| `GetEmrUser()` (REST GET /user/new) | `Patcher::OnGetEmrUser()` | **Active만** |
| `GetEmrOrder()` (REST GET /ordr/new) | `Patcher::OnGetEmrOrder()` | **Active만** |
| `IsExist*` / `SetDeptCode` / `SetExamCode` / `SetPatient` / `SetUser` | **Commander 내장 로직으로 대체** (`CISBrokerJobCommander.cpp` 1120~1163행) | Active만 |
| `SetOrder()` (`PkgOrder.SetOrder`) | `CISInBrokerJobWorker` 내장 (159행) | Active + Standby |
| `UpdEmrUser()` / `UpdEmrOrder()` (REST POST /prss) | `Patcher::OnUpdateEmr_UserResult()` / `OnUpdateEmr_OrderResult()` | **Active만** |

**즉 REST 호출은 전부 Active 노드에서만 발생하고, CIS DB 쓰기만 양 노드에 분산됩니다.** EHR API Gateway 입장에서는 호출 주체가 항상 1대이므로 API 호출량이 늘지 않는다는 장점이 있습니다.

## E-2. ⚠ EMR 결과 통보 시점 변경 — 가장 주의할 동작 차이

**현행 고대**: `PkgOrder.SetOrder` 성공 → REST POST `/ordr/prss` 로 EMR에 처리완료 통보

**CISDualBrokerLib**: `CISBrokerJobCommander.cpp` 1180~1186행

```cpp
if(DistributeJobToWorker(pCommand, order))          // ← T_INBROKERWORKERJOB INSERT 성공 시점
    m_pPatcher->OnUpdateEmr_OrderResult(order, TRUE);
else
    m_pPatcher->OnUpdateEmr_OrderResult(order, FALSE);
```

**작업 큐 등록에 성공한 시점**에 EMR로 성공 통보가 나갑니다. 이후 Worker의 `PkgOrder.SetOrder`가 실패해도 **EMR은 이미 성공으로 알고 있습니다.**

이는 서울성모에서는 EMR이 같은 Oracle 인스턴스이고 READYN 플래그만 갱신하므로 감내 가능한 설계지만, **고대는 외부 EHR REST 호출**이라 의미가 다릅니다. 처방 누락 시 EHR 쪽에 재전송을 요청할 근거가 사라집니다.

**대응 방안**

| 안 | 내용 | 평가 |
| --- | --- | --- |
| ① 그대로 수용 | 실패 건은 `T_INBROKERWORKERJOB.BWJ_RESULT`로 모니터링 | 구현 0. 운영 리스크 존재 |
| **② 통보 지연 (권장)** | `OnUpdateEmr_OrderResult` 를 no-op 처리하고, Worker 처리 완료 후 별도 경로로 REST POST | 라이브러리 수정 없이 Patcher만으로 가능. 단 Worker → Patcher 콜백이 없으므로 별도 감시 스레드 또는 `OnPeriodicWork` 활용 필요 |
| ③ 라이브러리 확장 | `CISInBrokerJobPatcher`에 `OnJobCompleted()` 콜백 추가 | 가장 정확. 라이브러리 분기 발생 |

**②의 구체안**: `CISInBrokerJobPatcher::OnPeriodicWork(CISDatabase& CISDB, int& reCallSec)` 가 `CISInBrokerJobCommander::OnDistributeJob()` 선두에서 주기 호출됩니다(431~465행). **Active 노드에서만 실행**되므로 통보 주체가 1대로 유지된다는 점이 이 방식의 장점입니다. 여기서 `T_INBROKERWORKERJOB` 의 완료 건(`BWJ_ENDDT < 9999…` AND 미통보)을 조회해 REST POST 하는 방식이 라이브러리 무수정으로 가능합니다. 단 "미통보" 여부를 판별할 컬럼이 없으므로 `BWJ_RESULT` 값 규칙(예: 성공 시 `'SUCCESS'` → 통보 후 `'SUCCESS_NOTIFIED'`)을 정하거나 별도 이력 테이블이 필요합니다.

**이 항목은 착수 전 반드시 의사결정이 필요합니다.**

## E-3. 부서 권한(`SetDeptAuthority`) 처리

현행 `Worker::SetDeptAuthority()` 는 `PkgAuthority.SetAuthorityFunctionInDept` 를 호출합니다.

CISDualBrokerLib는 이를 `Factory.Start(setting, pPatcher, NULL, &g_AuthirityNames)` 의 **4번째 인자**로 받아 `CISInBrokerJobCommander::SetAuthority()` 에 전달하는 구조입니다 (서울성모 `CISInbrokerDlg.cpp` 514행).

**작업**: 고대의 권한 코드 목록을 `CStringArray` 로 구성해 동일하게 전달. 현행 `Worker.h` 66행의 `m_AuthirityNames` 를 그대로 옮기면 됩니다.

## E-4. `EquipConfig` / 장비 설정

`EquipConfig` (Monitoring / CISReceiver 타입) 는 이중화와 무관하나, **양 노드가 동일한 장비 설정 파일을 가져야** 처리 결과가 일관됩니다. 설정 파일 동기화 절차를 배포 문서에 포함하십시오.

## E-5. `ConfigManager`에 `SearchDay` 추가

`CISOutBroker\ConfigManager.h` 에는 `nSearchDays` 가 있으나 **`CISInBroker\ConfigManager.h` 에는 없습니다**. `BROKER_SETTING.m_nSearchPeriod` 는 InBroker에서도 `OnGetEmrOrder(arOrder, nSearchDay)` 인자로 쓰이므로 신규 추가가 필요합니다.

# G. 배포 / 운영

## G-1. 서버 구성

| 항목 | 내용 |
| --- | --- |
| 노드 수 | 2대 (1호기 / 2호기) |
| 설치 경로 | 양 노드 동일 권장 (`C:\INFINITT\CISInBroker\`). 단 `ModuleConfig.ini`의 `Name`은 서로 달라야 함 |

| 서비스 등록 | 기존 `CISNTService` 방식 유지 (`ExecutionMode`) |

## G-2. 최초 기동 순서

1. DB에 A-1, A-2 반영 및 컴파일 오류 없음 확인
2. 1호기 기동 → `T_BROKERCOMMANDER` 에 1행 등록(Standby) 확인 → 20초 내 Active 승격 확인
3. 2호기 `ModuleConfig.ini` 의 `Name` 값이 **비어 있는지 확인** 후 기동 → 2번째 행 등록(Standby) 확인
4. `BC_ALIVEDT` 가 양쪽 모두 2초 간격으로 갱신되는지 확인

```sql
SELECT BC_KEY, BC_COMMANDTYPE, BC_COMMANDER, BC_STATE, BC_ALIVEDT, BC_LASTWRITERIP
FROM T_BROKERCOMMANDER
WHERE BC_ENDDT = TO_DATE('99991231235959','YYYYMMDDHH24MISS')
ORDER BY BC_COMMANDTYPE, BC_KEY;
```

## G-3. 모니터링 항목

| 항목 | 쿼리/방법 | 임계 |
| --- | --- | --- |
| Active 부재 | `BC_STATE='Active'` 행 수 | 0이면 즉시 경보 |
| Active 중복 | 동일 `BC_COMMANDTYPE` 내 Active 2개 이상 | 승격 경합 발생. 조사 필요 |
| Heartbeat 지연 | `SYSDATE - BC_ALIVEDT` | 20초 초과 시 경보 |
| 큐 적체 | `T_*WORKERJOB` 미완료 건수 | 기준선 대비 급증 시 경보 |
| 처리 실패 | `BWJ_RESULT NOT LIKE 'SUCCESS%'` | 일 단위 집계 |

## G-4. 롤백 계획

애플리케이션만 구 버전 EXE로 되돌리면 즉시 복구됩니다 (`PKGBROKER`와 신규 테이블은 남아 있어도 구 버전이 참조하지 않음). 단 A-4 ①안을 채택하지 않은 경우, 이중화 운영 기간 중 처리된 Outbound의 `HandleFlag` 의미가 달라 **롤백 시점의 미처리 건 재판정 절차**가 필요합니다.
